# API Requests

This directory contains a [Bruno](https://www.usebruno.com/) collection for exploring and validating MuleSoft’s MCP integration, management, and governance capabilities. The collection currently focuses on JWT authentication and persona-based authorization for MCP tools exposed through MuleSoft MCP Bridge and Anypoint Omni Gateway.

The collection uses the [OpenCollection](https://www.opencollection.com/) format, with requests stored as text files and versioned alongside the supporting scripts and Cedar authorization policies. The experiments require a deployed MCP endpoint configured with the appropriate Omni Gateway policies.

## Using the Collection

Open the `api-requests` directory in Bruno and select the environment for the target MCP endpoint (currently `env-demo-dev`). Run individual requests or use the collection runner to execute the authorization scenarios in sequence.

> [!IMPORTANT]
> The collection uses **Developer Mode** for JavaScript pre-request scripts that read locally generated JWT files. Enable this mode only for collections you trust, since scripts in Developer Mode can access local files and execute system commands.

  - `support-agent/` — Tool invocation tests for the Support Agent persona.

- `environments/` — Environment-specific MCP endpoint configuration.
- `opencollection.yml` — OpenCollection metadata and collection-level configuration.

## Environments

The collection currently defines one Bruno environment, `env-demo-dev`, which provides the `mcpUrl` variable identifying the MCP endpoint. Select this environment before executing requests.

```text
POST {{mcpUrl}}
```

> [!WARNING]
> Environment-specific files containing private configuration should remain uncommitted; use example files where needed to document required variables.

## Authentication and Authorization

### JWT Generation

JWTs are generated by the Python utility in `../scripts/generate-token.py` and stored under `../credentials/`, outside the Bruno collection. The `credentials/` directory is excluded from Git.

From the `mcp-governance` repository root, generate the required JWTs:

```bash
# Valid Employee JWT
python scripts/generate-token.py employee > credentials/employee.jwt

# Employee With Incorrect Audience
python scripts/generate-token.py employee --wrong-audience > credentials/employee-wrong-audience.jwt

# Employee With Expired Jwt
python scripts/generate-token.py employee --expired > credentials/employee-expired.jwt

# Valid Support Agent JWT
python scripts/generate-token.py support-agent > credentials/support-agent.jwt

# Valid Administrator JWT
python scripts/generate-token.py administrator > credentials/administrator.jwt
```

Folder-level pre-request scripts load JWT files using `bru.cwd()` and populate Bruno runtime variables. This avoids copying tokens into Bruno environments or committing credentials.

### JWT Authentication

The authentication scenarios cover:

| Request | Expected HTTP status |
| --- | --- |
| Missing JWT | `400 Bad Request` |
| Valid JWT | `200 OK` |
| Expired JWT | `401 Unauthorized` |
| Wrong Audience | `401 Unauthorized` |

The wrong-audience token must still have a valid signature and an unexpired `exp` claim so the test isolates audience validation. Regenerate short-lived tokens as needed before running the collection.

### Persona Authorization

The three persona folders exercise the same seven MCP tools against the authorization rules configured in Omni Gateway.

| MCP tool | Employee | Support Agent | Administrator |
| --- | :---: | :---: | :---: |
| `list_incidents` | Allow | Allow | Allow |
| `get_incident` | Allow | Allow | Allow |
| `create_incident` | Allow | Allow | Allow |
| `add_incident_comment` | Allow | Allow | Allow |
| `assign_incident` | Deny | Allow | Allow |
| `update_incident` | Deny | Allow | Allow |
| `delete_incident` | Deny | Deny | Allow |

Each request sends a JSON-RPC `tools/call` message to the MCP endpoint with the corresponding persona's JWT.

#### Response Validation

The Bruno **Tests** tab contains JavaScript assertions for permitted and denied operations:

- **Permitted operations:** verify that no JSON-RPC error is present and that `result.isError` is `false`. Incident creation also checks for HTTP `201 Created`.
- **Denied operations:** verify the JSON-RPC authorization error code `-32008` and message `Unable to access`.

Denied MCP tool calls can return HTTP `200 OK`, so HTTP status alone is not sufficient to validate authorization behavior.

### Repeatable Incident Scenarios

The collection uses `{{incidentId}}` to reference incidents created during testing. A response script on **Create Incident** parses the JSON-encoded incident in `result.content[0].text` and saves its ID as a Bruno runtime variable. Requests then use that variable for subsequent incident operations, including attempts that should be denied. This ensures the authorization checks target an existing incident rather than introducing a separate not-found condition.

For a full collection run, execute requests in their configured sequence:

1. Run the authentication scenarios.
2. Run Employee requests, including incident creation and denied-operation checks.
3. Run Support Agent requests, including permitted updates and denied deletion.
4. Run Administrator requests, with successful incident deletion last.

Each persona creates its own test incident and updates the incidentId runtime variable. Subsequent requests operate on that incident. The Administrator’s final deletion removes only the most recently created incident; earlier test incidents remain until explicitly deleted or the Service Desk API’s data is reset.
